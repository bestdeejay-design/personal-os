# 🧭 Personal OS — личный операционный центр

> **Статус:** Спецификация v2 (после продуктового аудита). Код не написан.
> **Принцип:** документ **изменяем** на любом этапе. Фазы — не контракт, а
> порядок сборки: сначала каркас, на нём всё остальное.

---

## TL;DR (для нетехна)

**Что это.** Личный «операционный центр» на твоём MacBook: заметки, канбан-задачи,
файлы, календарь и напоминания в одном месте, разложенные по профилям
(Работа / Дом / Семья / Друзья), которые можно накладывать друг на друга.
Поверх данных работает **агент**, который держит тебя «в тонусе»: спрашивает,
как прошла встреча, напоминает уточнить статус у коллег, ставит созвоны.

**Кто.** Один человек (ты). Профили — это фильтры, не отдельные аккаунты.

**Как запускается (Этап 1).** Один раз `docker compose up` в OrbStack →
открываешь `http://localhost:8080` в браузере. Всё локально, бесплатно, приватно.

**Как развивается.** Каркас (Этап 1) → агент + голос (Этап 2) → пересечения
плоскостей и приоритизация (Этап 3) → нативная обёртка Tauri 2 + доступ с
телефона (Этап 4).

**Главное ограничение Этапа 1.** Уведомления агента доходят, пока открыт браузер
(копятся в «входящих агента» и показываются при открытии) + опц. озвучка через
`say`. Настоящие OS-пушы на закрытое приложение — только на Этапе 4 (Tauri).

## 1. Философия и видение

Personal OS — не чатбот и не отдельная доска. Это **единое место**, где данные
живут в виде **пересекающихся плоскостей**, и **агент держит в тонусе**.

1. **Плоскости данных.** Не один список, а измерения: профиль, время (календарь),
   статус (канбан), содержание (заметки/файлы). Они **визуально пересекаются**,
   чтобы не путаться.
2. **Агент «в тонусе».** Не пассивная БД. Видит встречу → спрашивает «как прошла»;
   видит проект → напоминает уточнить статус; накладывает план проекта на график.
3. **Профили с наложением.** Один набор данных, несколько логических профилей.
   Смотреть отдельно или накладывать (Работа + Семья на неделю).
4. **Локально сейчас, нативно потом.** Этап 1 — OrbStack + браузер. Этап 4 — Tauri.
5. **Бесплатно.** OrbStack (личное), PostgreSQL, Node, Ollama + `:cloud` free-tier,
   Tauri — без платных подписок.

## 2. Пользователь и сценарии

**Кто:** один человек, владелец MacBook. Профили — логические теги, не аккаунты.

**S1. Заметка после встречи.** Запланирована «Синк с командой» 14:00. В 14:05
агент спрашивает: «Как прошла? Что важного?». Юзер надиктовывает итог → агент
сохраняет заметку, привязывает к встрече и проекту, ставит задачу «Уточнить у
Пети про дизайн» в профиль Работа.

**S2. Проект и задачи.** Проект «Запуск Lovii v2» + канбан (Бэклог→В работе→
Сделано). Агент: «3 задачи без ответственного/дедлайна — уточни у коллег»,
предлагает созвон и ставит его в календарь.

**S3. День и неделя.** Утром — вью «Сегодня»: встречи + задачи с дедлайном сегодня
+ напоминания агента. Отдельно — «Неделя» с наложением профилей.

**S4. Пересечение плоскостей.** Вью «Всё сразу»: календарь (по времени) + задачи
(по дедлайну) + заметки (по дате) наложены в одной ленте; фильтр по профилю;
конфликты времени подсвечены.

**S5. Файлы.** К заметке/задаче крепится фото прототипа или PDF-спецификация;
файл лежит локально, доступен из веба.

**S6. Приоритизация как процесс.** Задачи с весом; агент предлагает переприоритет:
«X блокирует Y — повысить?». Есть вью, где тащишь задачи и порядок пересчитывается.

## 3. Функциональные требования (по модулям, с фазами)

Колонка **Этап** — когда функция появляется. P1=Каркас, P2=Агент+Голос,
P3=Глубина, P4=Натив.

### 3.1 Профили — P1

| Требование | Детали |
|-----------|--------|
| Дефолтные | Работа, Дом, Семья, Друзья + создание своего |
| Переключение | Активный профиль фильтрует данные в UI |
| Наложение | Выбор нескольких → данные суммарно |
| Природа | Логический тег на сущности (`profile_ids[]`); данные физически общие |
| Визуал | У каждого профиля свой цвет (исп. в оверлее) |

### 3.2 Заметки — P1 (голос — P2)

| Требование | Этап | Детали |
|-----------|------|--------|
| Формат | P1 | Markdown |
| Поля | P1 | title, body_md, profile_ids[], tags[], linked_meeting/project/task, timestamps |
| Поиск | P1 | Полнотекст + семантический (RAG/Ollama) |
| Голосовой ввод | **P2** | Диктовка заметки (STT из voice-assistant) — **ядро, не опция** |
| Связи | P1 | Привязка к встрече/проекту/задаче |
| Архив | P3 | Скрытие старых без удаления |

### 3.3 Канбан-задачи — P1

| Требование | Этап | Детали |
|-----------|------|--------|
| Колонки | P1 | Бэклог / В работе / Сделано (+ свои) |

### 3.4 Файлы — P1

| Требование | Этап | Детали |
|-----------|------|--------|
| Прикрепление | P1 | К заметке/задаче/проекту |
| Хранение | P1 | Локально в volume OrbStack |
| Метаданные | P1 | filename, mime, size, owner, uploaded_at |
| Превью | P1 | Картинки — превью; PDF — скачивание |
| Общий «файловый инбокс» | P3 | Закинуть файл без привязки, привязать потом |

### 3.5 Календарь — P1 (экспорт P1, импорт P4)

| Требование | Этап | Детали |
|-----------|------|--------|
| События | P1 | title, start, end, all_day, profile_ids[], linked_project, notes, location |
| Вью | P1 | День / Неделя / Месяц / Список |
| Напоминания | P1 | За N минут (только внутренние события) |
| Экспорт | P1 | `.ics` (импорт в Apple/Google вручную) |
| Рекуррентность | P3 | Повтор встреч (стендап/отчёт) |
| Конфликты | P3 | Детект пересечений по времени, подсветка |
| Импорт CalDAV/OAuth | P4 | Двусторонняя синхронизация (вне Этапа 1) |

### 3.6 Уведомления и дайджесты — P1 (механика агента — P2)

| Требование | Этап | Детали |
|-----------|------|--------|
| Дайджест «Сегодня» | P1 | Встречи + задачи с due сегодня + напоминания |
| Обзор «Неделя» | P1 | Вью недели с наложением профилей |
| Доставка (Этап 1) | P1 | Показ при открытии UI + WebSocket, пока вкладка открыта; **иначе копится в Agent Inbox** |
| OS-пуш закрытое приложение | P4 | Через Tauri (Этап 4) |
| Агент-тонус | P2 | См. раздел 5 |

### 3.7 Проекты — P1

| Требование | Этап | Детали |
|-----------|------|--------|
| Сущность | P1 | name, desc_md, profile_ids[], status, goal |
| Связи | P1 | Проект ← задачи / встречи / заметки |
| План → график | P3 | Наложение задач проекта на календарь, предложение созвонов |

### 3.8 Агент «в тонусе» — P2 (см. раздел 5)

Триггеры, условия, частота, DND, inbox. Ядро ценности, но **поверх каркаса**.

### 3.9 Поиск / RAG — P1

Полнотекст (SQL) + семантический (Ollama). Единый поиск по заметкам/задачам/
встречам/файлам с учётом профиля.

### 3.10 Голос — P2 (ядро для пользователя)

Диктовка заметок (STT) + озвучка напоминаний (`say`). Переиспользуем из
voice-assistant. **Не опция** — сценарий S1 строится на диктовке.

### 3.11 Импорт извне — P3 (опц.)

Apple Notes / Things / Notion → заметки/задачи. Путь миграции для принятия.

### 3.12 Аналитика — P3 (опц.)

«Где время уходит», «сколько задач закрыто», загрузка по профилям.

## 5. Поведение агента (детально) — Этап 2

> Перенесено из декларации в механику. Без этого раздела разработчик сделает
> «просто напоминалку».

### 5.1 Триггеры

| Триггер | Условие | Действие агента |
|---------|---------|-----------------|
| Встреча завершилась | `end < now` И нет заметки с `linked_meeting` | Спросить «Как прошла? Что важного?» (Agent Inbox) |
| Задача без ответственного/дедлайна в проекте | проект активен | Напомнить «Уточни у коллег статус» |
| Блокировка | задача X блокирует Y | Предложить повысить приоритет X |
| Дедлайн близко | `due_date` ≤ через 2 дня | Напомнить |
| План проекта | есть задачи без дат | Предложить созвон + поставить в календарь |

### 5.2 Условия «не спамить»

- **DND-окно:** глобальное (и опц. по профилю) время «не беспокоить» (напр. 22:00–8:00).
- **Лимит:** не более N напоминаний в день (настраивается, дефолт 5).
- **Контекст:** не спрашивать «как прошла» о встрече без проекта/участников/названия.
- **Подтверждение:** агент **предлагает** действие (создать заметку/задачу/встречу),
  не выполняет разрушительно без окей.

### 5.3 Agent Inbox (входящие агента)

- Сообщения агента копятся в `AgentMessage` (resolved_bool).
- Показываются при открытии UI (если вкладка была закрыта — ничего не потеряно).
- Юзер отвечает: принять предложение / отклонить / ответить текстом (диктовкой).
- Это решает проблему доставки в Этапе 1 (нет OS-пуша при закрытом приложении).

### 5.4 Доставка в Этапе 1

- WebSocket-пуш, **пока вкладка открыта**.
- Иначе — копится в Inbox, показывается при следующем открытии.
- Опц. озвучка напоминаний через `say` (только когда MacBook рядом).
- **Полноценный OS-пуш на закрытое приложение — Этап 4 (Tauri).**

## 6. Визуализация пересечений и приоритизация — Этап 3

### 6.1 Оверлей профилей (ASCII-мокап)

```
Неделя: [Работа] + [Семья]        цвета: Р=синий, С=зелёный
Пн  09:00 [Р] планёрка       19:00 [С] ужин с семьёй
Вт  14:00 [Р] синк            -- свободно
Ср  !! КОНФЛИКТ !!           12:00 [Р] созвон + 12:00 [С] врач  ← подсветка красным
Чт  ---
Пт  17:00 [Р] релиз         20:00 [С] кино
```
Конфликт (две сущности в одно время в наложенных профилях) → красная подсветка
и предложение перенести.

### 6.2 Вью «Всё сразу» ( united timeline)

```
08:00 [Встреча] Синк            (календарь)
08:45 [Задача]  Написать спец  due:сегодня  pri:High  (канбан)
09:30 [Заметка] Идея по дизайну             (заметки)
12:00 [Встреча] Обед с Петей
14:00 [Задача]  Уточнить у Пети pri:Med  (канбан, от агента)
```
Одна лента по времени; слева — тип/цвет; фильтр по профилю сверху.

### 6.3 Приоритизация как процесс

- Вью «Приоритеты»: список задач, сортируемый перетаскиванием (rank).
- Каждая задача: `priority` (enum) × `weight` (число) → итоговый ранг.
- Агент предлагает перестановки (см. 5.1 «Блокировка»), юзер принимает/отклоняет.
- Пересчёт ранга — при каждом изменении (не разовое поле).

## 7. Архитектура (Этап 1, OrbStack)

```
macOS (MacBook)
┌──────────────┐      ┌──────────────────────────────┐
│  Браузер     │ HTTP │  OrbStack (docker-compose)    │
│  React+Vite  │◄────►│  ┌────────────────────────┐  │
│  localhost   │      │  │  app-server (Node)       │  │
│              │      │  │  REST + WebSocket        │  │
│              │      │  │  agent-worker            │  │
│              │      │  │  RAG/Ollama клиент       │  │
│              │      │  └───────────┬────────────┘  │
│              │      │  ┌───────────▼────────────┐  │
│              │      │  │  PostgreSQL (volume)    │  │
│              │      │  └───────────┬────────────┘  │
│              │      │  ┌───────────▼────────────┐  │
│              │      │  │  volume ./data (файлы)  │  │
│              │      │  └────────────────────────┘  │
│  Ollama      │      └──────────────────────────────┘
│ (вне конт.,  │◄──── host.docker.internal:11434
│ локально)    │
└──────────────┘
```

**Переносимость.** Весь стек — один `docker-compose.yml`. Чтобы перенести
(Этап 4): меняем `OLLAMA_HOST`/`DB_HOST`, пробрасываем порт, volume едет с данными.
Поэтому PostgreSQL — в контейнере (один артефакт, легко перенести).

## 8. Модель данных (логическая)

```
Profile (id, name, color, is_default)
Note (id, title, body_md, profile_ids[], tags[], created_at, updated_at,
      linked_meeting_id?, linked_project_id?, linked_task_id?, archived_bool)
Task (id, title, desc_md, status, priority, weight, assignee, due_date?,
      recurrence?, project_id?, profile_ids[], created_at, archived_bool)
Project (id, name, desc_md, profile_ids[], status, goal?, created_at)
Meeting (id, title, start, end, all_day, profile_ids[], linked_project_id?,
         notes_md, location?, recurrence?)
FileMeta (id, filename, mime, size, owner_type, owner_id, stored_path, uploaded_at)
Reminder (id, type, fire_at, message, related_entity_type?, related_entity_id?,
          fired_bool, profile_ids[])
AgentMessage (id, trigger, text, suggested_actions_json, created_at,
               resolved_bool, profile_ids[])
Setting (key, value)   -- DND-окно, лимит напоминаний и т.п.
```

Связи: Project 1—N Task/Meeting; Note N—1 сущность; все тегируются `profile_ids[]`;
Reminder/AgentMessage ссылаются на любую сущность.

`recurrence` (упрощённо): `none | daily | weekly | monthly` + `interval` + `until`.
`archived_bool` — soft-delete (P3).

## 10. Этапы разработки (итоговая разбивка)

### Этап 1 — Каркас (MVP, локально)
- `docker-compose.yml` (postgres + app) + volume данных.
- Сервер: REST + WebSocket, RAG-клиент (Ollama).
- БД: миграции (Profile, Note, Task, Project, Meeting, FileMeta, Reminder, Setting).
- Фронт: профили (переключение), заметки (MD+поиск), канбан (drag&drop),
  календарь (день/неделя), файлы (загрузка), дайджесты (сегодня/неделя),
  поиск (полнотекст+RAG).
- **Не входит:** агент-поведение, голос, рекуррентность, конфликты, приоритизация-процесс.

### Этап 2 — Агент «в тонусе» + Голос
- Механика агента (раздел 5): триггеры, DND, inbox, предложения.
- Голос: диктовка заметок (STT), озвучка напоминаний (`say`).
- Продолжение сценария S1 вживую.

### Этап 3 — Глубина
- Пересечения плоскостей (оверлей + «всё сразу» + конфликты) — раздел 6.
- Приоритизация-как-процесс (воркфлоу + вью).
- Рекуррентность, архив/удаление, общий файловый инбокс.
- Импорт извне (опц.), аналитика (опц.).

### Этап 4 — Натив + доступ извне
- **Tauri 2** обёртка поверх фронта: нативное окно Mac (WKWebView), системные
  уведомления macOS, малый дистрибутив (3–20 МБ).
- **Мобильная обёртка** Tauri 2 (iOS/Android) — та же кодоваза.
- **Вынос сервера:** хостинг/tunnel → доступ по URL с телефона.
- **Аккаунты:** регистрация, сессия; профили привязываются к аккаунту
  (логические профили Этапа 1 переиспользуются).
- **Синхронизация:** один бэкенд, несколько устройств.
- **Календарь:** двусторонняя интеграция (CalDAV/Google).
- **OS-пуш** закрытого приложения (через Tauri).

> Решения Этапа 4 принимаются позже, когда каркас обкатается. Ядро (БД+сервер+API)
> не меняется — меняется обёртка и точка входа.

## 16. Дизайн (требования к UI) — P1

> Пользователь сформулировал: «сделаем локанично, тёмная и светлая тема,
> акценты настраиваемые (выбор цвета), на старте заданы яркие цвета,
> типа оранжевого».

### 16.1 Темы
- **Тёмная и светлая** — переключатель в UI, выбор сохраняется в `Setting`.
- Дефолт — **тёмная** (как в связанных проектах).
- Контраст/читабельность — минимальный уровень доступности (не резать глаза).

### 16.2 Акцент (настраиваемый)
- **Пользователь выбирает акцентный цвет** (цветовой пикер), сохраняется в `Setting`.
- Акцент применяется ко всем интерактивным элементам (кнопки, активные вкладки,
  выделение профиля, индикаторы приоритета).
- Реализация: CSS-переменные (`--accent`), значение задаётся из настроек.

### 16.3 Дефолтные яркие цвета (на старте)
- На первом запуске задан **яркий акцент — оранжевый** (`#FF7A00` или близко).
- Профили по умолчанию получают яркие, различимые цвета:
  - Работа — оранжевый `#FF7A00`
  - Дом — зелёный `#2FBF71`
  - Семья — синий `#3B82F6`
  - Друзья — фиолетовый `#A855F7`
- Цвет профиля используется в оверлее/календаре/тегах (раздел 6).

### 16.4 Принципы
- **Локанично** (минимализм): меньше визуального шума, чёткая иерархия.
- Единая дизайн-система: переменные цветов/радиусов/отступов, переиспользуемые компоненты.
- Адаптивность: комфортно на десктопе (Этап 1), готовность к мобильным (Этап 4).
